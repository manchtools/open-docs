# Proposal: runtime content pipeline (0.4.0)

**Status:** implemented on the `0.4.0-runtime-content` branch — measured
results: a 256 MB container ingests mounted content in ~1.7 s at ~92 MiB
(120-page default docs: ~106 MiB, search indexed at boot); validation
fails the boot with file:line errors; rebranding via PUBLIC_* needs no
rebuild. The estimates below were the pre-implementation projections.
**Goal:** ingest user content on low-memory hosts (~256 MB) by treating
Markdoc files as *data rendered at runtime* instead of *code compiled
through Vite*.

## Problem

Today every `.md` file is compiled into a Svelte module by
`svelte-markdoc-preprocess`, and the whole site is prerendered by Vite.
That build peaks at **~1.7 GB** (measured; the floor is Vite/Rollup
bundling the app itself — content adds little). The container runs this
build at start whenever content is mounted, so hosts under ~2 GB cannot
ingest content at all; they must bake an image on a bigger machine.

Build-time validation is not a real loss: mounted content is already only
validated by the *container-start* build, i.e. at the same moment a boot
pass would validate it. Only the bundled default docs lose CI-time
validation, and a CI job that boots the container restores that.

## Measured anchors

| What | Cost |
|---|---|
| Current content rebuild (Vite) | ~1 724 MB peak, ~18 s local / minutes on small VPS |
| Markdoc parse + validate + transform, **all 116 files** | **61 ms total (0.53 ms/page), ~130 MB RSS — ~80 MB of which is the Bun runtime baseline** |
| Pagefind indexing (120 pages) | ~53 MB |
| Serving a built site | ~27 MB |

## Architecture

The **app shell** (layout, nav chrome, components, vendored Mermaid/Shiki)
is still compiled with Vite — once, at *image build*, on our CI, where RAM
is plentiful. Mounted content never goes through Vite again:

```
container boot
  1. scan content dir        → slugs, languages, nav tree, frontmatter, meta
  2. per page: tokens → heading anchors → Markdoc.parse → validate → transform
  3. fail-fast on validation errors (unknown tag/attr, broken internal link)
  4. warm pass: SSR-render every route, cache HTML in memory/disk
  5. Pagefind over the rendered HTML → static search index
  6. serve (cached HTML for content routes; SvelteKit for the rest)
```

### 1. Runtime content store (replaces `import.meta.glob`)

`src/lib/server/content-store.ts`: walks the content dir with `fs` at
boot and produces the exact structures `nav.ts` / `content.ts` /
`pageMeta` derive today. The pure logic (slugging, i18n path splitting,
ordering, frontmatter) already lives in `slug.ts` / `i18n.ts` and is
unit-tested — it is reused as-is; only the *source* changes from build-time
glob to runtime scan.

### 2. Markdoc schema from the existing component registry

`svelte-markdoc-preprocess` auto-derives tag attributes from component
props ("new prop = new attribute"). To keep that property, a small script
runs at **image build** and emits `markdoc.schema.json` from
`tags.svelte` / `nodes.svelte` + component props — same source of truth,
now consumed at runtime by `Markdoc.validate`/`transform`. The two
existing preprocessors (token replacement, heading anchors incl. the
ASCII-fold/hash slugger) port verbatim into this step — they are plain
string/AST transforms with no Vite dependency.

### 3. Tree renderer (the main new code)

A recursive Svelte component renders Markdoc's transformed tree:

```svelte
<!-- MarkdocTree.svelte (sketch) -->
{#if typeof node === 'string'}{node}
{:else if isComponentTag(node.name)}
  <Component this={components[node.name]} {...node.attributes}>
    {#each node.children as child}<Self node={child} />{/each}
  </Component>
{:else}
  <svelte:element this={node.name} {...node.attributes}>
    {#each node.children as child}<Self node={child} />{/each}
  </svelte:element>
{/if}
```

It maps tag names to the **same components used today** (Callout, Tabs,
Columns, CodeBlock, …) — no component changes. Works in SSR and in the
client; the transformed tree is plain JSON (`Tag {name, attributes,
children}`), so SvelteKit serializes it through `+page.server.ts` `load`
and hydration works unchanged (tabs, accordions, lightbox, copy buttons).
Estimated ~200–300 LOC plus parity tests against the current renderer's
HTML output.

### 4. Boot warm pass + search

After the server constructs, render every `lang × slug` route through
SvelteKit's own `server.respond()` (loopback), cache the HTML, and run
Pagefind over the cache (or feed it via Pagefind's Node API). Crawlers and
users get the cached HTML → **SSR and SEO (canonical/OG/hreflang/sitemap/
llms.txt) are unchanged**; search is unchanged including per-language
indexes (`<html lang>` is in the rendered pages). Content is read-only per
container run, so the cache never invalidates.

### 5. Runtime config

- `PUBLIC_*` move from `import.meta.env` to `$env/dynamic/public` → a
  rebrand no longer triggers any build at all.
- `theme.css` is served from the content dir as a `<link>` injected after
  the bundled stylesheet (same cascade position as today).
- CSP: keep the build-time nonce config; append the content-derived
  `frame-src` to the response header in `hooks.server.ts` at boot.
- **`BASE_PATH` stays build-time** (SvelteKit's base is compile-time). A
  sub-path deploy still rebuilds the shell (~1.5 GB) — the one remaining
  heavy path; documented as the exception.

### 6. Static export stays possible

The warm-pass cache *is* a static site. An `open-docs export` command
writes it out, preserving today's "host the build output anywhere static"
deployment mode for those who want it.

## Expected savings (content ingestion on a host)

| | Today (rebuild) | Proposed (boot pass) |
|---|---|---|
| Peak RAM | ~1 724 MB | **~150–250 MB** (Bun ~80 + trees/render + Pagefind ~53) — ≈ **85–90 % less** |
| CPU / wall | ~18 s local, minutes on a small VPS (full Rollup graph + minify) | **~2–5 s** for ~120 pages; ~0.5 ms/page parse+transform + ms-level SSR per page — ≈ **10×+ less**, scaling linearly with pages, flat in memory if rendered one page at a time |
| Min viable host | ~2 GB | **~256 MB** |

Parse/transform and Pagefind numbers are measured on this repo; SSR
render-per-page is the one estimated component (validated first in the
spike, milestone 1).

## Risks & mitigations

- **Renderer parity** (tables, nested tags, fences, heading ids): golden
  tests diffing rendered HTML of the bundled docs against the 0.3.x
  output before cutover.
- **Schema fidelity**: generated from the same components; a self-checking
  test asserts every export in `tags.svelte`/`nodes.svelte` appears in the
  schema (no hardcoded list).
- **Tree payload size** per client navigation: a transformed page is
  ~10–200 KB JSON; acceptable, and trimmable (drop nulls/locations).
- **One pipeline, not two**: the `svelte-markdoc-preprocess` path is
  removed in 0.4.0 (hard cutover). The image keeps `node_modules` only for
  the rare `BASE_PATH` shell rebuild.
- **Bundled-docs validation moves to CI**: a workflow job boots the
  container and fails on boot-validation errors.
